## 问题 1：为什么不能让每个业务类直接调用 `llmClient.chat.completions.create()`？

**考点**：横切关注点 / 分层

SDK 的 `create()` 只解决"把一次 HTTP 请求发出去"，它不解决任何工程问题。

如果每个业务类都直接调，会同时踩五个坑：

| 问题 | 具体表现 |
| --- | --- |
| 配置散落 | `model`、`temperature`、`maxTokens` 硬编码在各处，换模型要全项目搜 |
| 重复代码 | 超时、重试、日志、usage 统计，每个调用点重写一遍 |
| 无法统一治理 | 限流、成本核算、缓存、降级没有地方可以加 |
| 无法测试 | 业务类直接依赖全局单例 `llmClient`，mock 不掉 |
| 供应商锁定 | 将来换 SDK、加多模型路由，要改所有调用点 |

正确做法：**`LLMService` 是唯一出口**（门面 / Facade 模式）。

本工程的依赖方向是单向的：

```
09-java-code-assistant  →  Conversation  →  LLMService  →  llmClient
       （业务）              （会话）        （基础服务）     （SDK）
```

业务层只认识 `LLMService.chat()`，连 `llmClient` 都不 import。

> 注意：`01`~`06` 那些示例是**故意**直接调 `llmClient` 的 —— 教学需要让你先看见底层，
> 那不是工程写法。`08`、`09` 才是。

## 问题 2：为什么 Agent 需要 Token Usage？

**考点**：可观测性

四个理由，按重要性排：

1. **成本核算**：token 就是钱。Agent 执行一次任务可能调用 LLM 几十次，不统计就是黑洞。
2. **上下文管理**：`prompt_tokens` 逼近上下文窗口时必须裁剪历史或做摘要，
   不知道用量就没法做这个决策。
3. **预算控制**：知道单轮消耗，才能合理设置 `maxTokens`、限制轮数、超预算熔断。
4. **调试信号**：推理模型里 `reasoning_tokens` 占比异常偏高，
   往往说明 prompt 写得含糊，模型在反复纠结。

Agent 场景的正确姿势是**按"任务"聚合**，而不是按"请求"看：

```
用户一次提问
  └── LLM 调用 #1  prompt=2000  completion=300
  └── LLM 调用 #2  prompt=2500  completion=150
  └── LLM 调用 #3  prompt=2800  completion=800
  ─────────────────────────────────────────────
  本次任务合计     prompt=7300  completion=1250  ← 这才是要报给用户/计费的数字
```

代码对照：`LLMResponse` 的三个字段（`promptTokens` / `completionTokens` / `totalTokens`），
以及 `05-token-usage.ts` 里从 `response.usage` 取值。

## 问题 3：为什么 Timeout 和 Retry 通常应该放在 LLM 基础服务层？

**考点**：横切关注点归属

它们属于**通用工程策略**，和"这段业务要问什么"没有任何关系。

放在业务层的问题：

- 每个调用点都要写一遍，容易漏
- 策略不统一（有的 30 秒、有的 3 分钟）
- 业务代码被 `try/catch` 和重试循环污染，可读性崩坏
- 想调整策略，得改 N 个文件

放在服务层的收益：一处修改全局生效，业务代码只需关心"拿到结果"或"抛错"。

**但有件事只有服务层能做** —— 结合流式状态做重试判断：

```ts
// llm.service.ts
// 已经输出过内容就不能重试，避免重复打印
if (streamed) {
  break;
}
```

业务层根本看不到流的状态，它只知道"失败了"。这条规则注定属于服务层。

> `06-timeout.ts` 在调用点直接传 `timeout` 只是演示用法；
> 真实工程里应该下沉到 `LLMService`，由它统一兜底。

## 问题 4：为什么不是所有错误都应该 Retry？

**考点**：错误分类

重试的**唯一前提**是：这个错误是暂时的，再试一次有可能成功。

| 错误类型 | 例子 | 该重试吗 |
| --- | --- | --- |
| 网络抖动 | 连接重置、DNS 超时 | ✅ |
| 服务端 5xx | 500 / 502 / 503 / 504 | ✅ |
| 限流 429 | 请求过于频繁 | ✅ 但**必须退避** |
| 认证失败 401 / 403 | key 错、没权限 | ❌ |
| 参数错误 400 | `max_tokens` 超限、messages 格式错 | ❌ |
| 模型不存在 404 | 模型名拼错 | ❌ |
| 已输出一半 | 流中途断开 | ❌ 重试会出现重复内容 |
| 用户主动取消 | abort | ❌ 违背用户意图 |

无脑重试的三个危害：

1. **重试风暴**：服务端已经过载，你的重试让情况更糟
2. **白花钱**：注定失败的请求也重试 3 次，成本 ×3
3. **掩盖真问题**：key 错了却看到"重试 3 次后失败"，排查方向被带偏

还有个隐藏坑：**429 必须配指数退避 + 抖动**，立即重试只会加剧限流。

改进方向 —— 现在的 `catch` 是无差别重试，应该先分类：

```ts
const status = (error as { status?: number }).status;

// 没有 status 说明是网络层错误，可重试
// 429 和 5xx 可重试，其他 4xx 直接抛
const retryable =
  status === undefined || status === 429 || status >= 500;

if (!retryable || streamed) break;
```

## 问题 5：Streaming 是否意味着模型真正计算得更快？

**考点**：区分「感知延迟」和「真实耗时」

**不是。** 总计算量和总生成时间基本不变，流式改变的只是**你什么时候能开始看到结果**。

| 指标 | 非流式 | 流式 |
| --- | --- | --- |
| 首字时间（TTFT） | 等于总耗时 | 几百毫秒 |
| 总耗时 | 约 89 秒 | 约 89 秒 |

类比视频：**"下载完再播" vs "边下边播"**。总下载时间一样，但后者不用干等。

对推理模型尤其关键：思考阶段如果什么都不打印，看起来就是卡死 ——
这正是本课最开始遇到的那个问题（`reasoning_content` 没被打印）。

额外收益：

- 可以**提前中止**（用户不满意就取消，省下后续 token）
- 能观察思考过程，方便调 prompt

代价：

- 不能用"首字时间"衡量模型真实速度
- 错误处理更复杂：流中途断掉，已经输出的内容撤不回来
- 所以才有"`streamed` 之后不重试"这条规则

**结论：流式优化的是体验和可控性，不是算力。**

## 问题 6：为什么多轮对话需要不断传递历史消息？

**考点**：LLM API 是无状态的

核心认知：**每一次 HTTP 请求都是一次独立的、无状态的函数调用**，
服务端不保存你的会话，也没有"会话 ID"这种东西。

所谓"模型记得上文"，完全是应用层伪造出来的效果 —— 把历史拼进 `messages` 再发一遍。

代码对照 `conversation.service.ts`：

```ts
readonly messages: LLMMessage[] = [];
// 结构：system → user → assistant → user → assistant → ...
```

每轮 `ask()` 做三件事：

```ts
this.messages.push({ role: "user", content: userInput });   // 1. 追加本轮提问

const response = await this.llmService.chat(
  this.messages,   // 2. 把「整个数组」发出去，不是只发新问题
  { ...this.options, ...options },
);

this.messages.push({ role: "assistant", content: response.content }); // 3. 存下回答
```

**验证方法**：`09` 第二轮问"你刚才说的第二个问题怎么解决？" ——
"刚才""第二个"这些指代全靠历史才成立。把 `this.messages` 换成只发新问题，模型立刻就懵。

**代价**：prompt 越滚越大，成本接近平方级增长（详见 `多轮会话与token计费.md` 第六节）。

## 问题 7：Agent Loop 的 Token 成本和延迟会怎么变化？

```
LLM → Tool → LLM → Tool → LLM
```

**考点**：串行调用 + 上下文累积

### Token 成本：不是线性，接近平方级

两个原因叠加：

1. 每次 LLM 调用都要**重发前面所有内容**（历史）
2. **Tool 的返回结果也会进历史**，而且往往很大
   （读一个文件几千 token，一次搜索结果上万 token）

设每轮新增 P（prompt 增量）、C（输出）、T（工具结果）：

| 第几次调用 | prompt 大约包含 |
| --- | --- |
| 1 | P1 |
| 2 | P1 + C1 + **T1** + P2 |
| 3 | 上面全部 + C2 + **T2** + P3 |

那个 **T 就是工具返回值，它经常是 Agent 成本失控的主因** ——
很多工具返回一大坨 JSON，模型其实只需要其中两三个字段。

实测参考：本课三轮对话把 `maxTokens` 设成 3000，累计消耗接近 1.9 万 token。

### 延迟：严格累加，无法并行

```
总延迟 ≈ Σ(LLM 生成时间) + Σ(工具执行时间)
```

- LLM 必须先决定调哪个工具，工具结果必须喂回去才能继续 —— **天然串行**
- LLM 生成时间随 prompt 变长而增加（prefill 阶段更久）
- 所以 Agent 任务动辄几十秒到几分钟，比单次对话慢一个数量级

### 工程启示

| 手段 | 作用 |
| --- | --- |
| 设 `maxIterations` | 防止无限循环烧钱 |
| 统计 token 并设预算 | 超预算熔断 |
| 支持中断 / 取消 | 让用户能止损 |
| 上下文压缩 | 老历史做摘要，别无限堆 |
| 工具返回裁剪 | 只把模型需要的字段喂回去 |
| 并行调用独立工具 | 缩短延迟 |
| 小模型做简单决策 | 降成本 |
| Prompt Caching | 复用不变的 system prompt，省钱又提速 |

## 一句话总结

| 题目 | 一句话答案 |
| --- | --- |
| 1 | 业务层不该关心 HTTP，横切关注点要收口到服务层 |
| 2 | 没有 usage 就没有成本、预算和上下文管理 |
| 3 | 通用策略放服务层，且只有服务层看得见流的状态 |
| 4 | 重试的前提是错误可恢复，否则是浪费和放大故障 |
| 5 | 流式改善的是感知延迟，不是真实算力 |
| 6 | LLM API 无状态，"记忆"全靠应用层重发历史 |
| 7 | 成本接近平方级增长，延迟严格串行累加 |
