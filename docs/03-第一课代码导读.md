## ⚠️ 笔记要修正：temperature 已经不能用了

`本课知识.md` 里写"Temperature — 控制输出随机性"，这条在当前一代模型上已失效。

| 模型                                                      | `temperature` / `top_p` / `top_k` |
| --------------------------------------------------------- | --------------------------------- |
| `claude-opus-5`、`claude-sonnet-5`、`claude-opus-4-8/4-7` | ❌ 已移除，传了返回 **400**       |
| `claude-haiku-4-5` 及更老模型                             | ✅ 仍可用                         |

替代品是 `output_config.effort`：

```typescript
output_config: {
  effort: 'high';
} // low | medium | high | xhigh | max，默认 high
```

两者不是同一个东西：`temperature` 调**采样随机性**，`effort` 调**思考深度和 token 预算**。

用法建议：分类/抽取/闲聊用 `low`~~`medium`；写代码/多步推理/Agent 长流程用 `high`~~`xhigh`；
只在"正确性远比成本重要"时用 `max`。

## 01-hello.ts — 最小调用

三个必填字段：`model`、`max_tokens`、`messages`。

`max_tokens` 是**输出**上限，单位是 token（中文约 1 字 ≈ 1~2 token）。
它是硬截断，模型不知道这个限制存在。

`stop_reason` 取值：

| 值           | 含义                     |
| ------------ | ------------------------ |
| `end_turn`   | 正常说完                 |
| `max_tokens` | 撞上限被截断，需调大     |
| `tool_use`   | 模型要调工具（后面课程） |
| `refusal`    | 模型拒绝了               |

`message.usage` 每次都该看一眼，它直接对应账单（输出单价通常是输入的 5 倍）。

## 02-system-and-effort.ts — System 与 effort

`system` 是**独立字段**，不放在 `messages` 里。为什么不能塞进 user 消息：

1. **权威层级不同** —— 模型对 system 更听话，这是防提示注入的基础。
   塞进 user 消息，用户下一句话就能推翻它。
2. **缓存友好** —— system 通常固定，独立字段有利于提示缓存命中，省钱。

## 03-streaming.ts — 流式输出

```typescript
for await (const event of stream) {
  if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
    process.stdout.write(event.delta.text); // 用 write，不用 log（否则每块换行）
  }
}
const finalMessage = await stream.finalMessage(); // 流跑完还能拿完整对象
```

- 判断要写两层：`event.type` 和 `event.delta.type`（delta 也有多种）
- 别自己拼字符串攒结果，用 SDK 的 `stream.finalMessage()`
- `max_tokens` 开很大时（如 64000）**必须**用流式，否则会 HTTP 超时

## 04-chat-history.ts — 多轮对话

**核心认知：Claude API 是无状态的。** 服务端不记得上一轮，"多轮对话"完全靠客户端
把历史重发一遍造出来。

```typescript
history.push({ role: 'user', content: userInput });
const message = await client.messages.create({ model, max_tokens, messages: history });
history.push({ role: 'assistant', content: collectText(message) }); // ← 少了这行模型就"失忆"
```

跑一下看 `input_tokens` 逐轮变大 —— 这就是 Context Window 的现实约束：
历史越长越贵越慢，超窗口直接报错。所以真实 Agent 必须做上下文管理（截断、摘要压缩）。

用 SDK 的类型，别自己定义：

```typescript
const history: Anthropic.MessageParam[] = []; // ✅
interface ChatMessage {
  role: string;
  content: string;
} // ❌ 丢类型安全，且和 SDK 升级脱节
```

## 05-structured-json.ts — 结构化输出

**要戒掉的坏习惯**：在 prompt 里求模型返回 JSON，然后 `JSON.parse`。
模型偶尔会多写一句解释、用 ``` 包起来、少个引号 —— 演示能跑，生产随机崩。

**正确做法**：把 Zod schema 交给 API，服务端保证结构。

```typescript
const response = await client.messages.parse({        // 注意是 parse，不是 create
  model: resolveModel(),
  max_tokens: 2048,
  messages: [...],
  output_config: { format: zodOutputFormat(BugReportSchema) },
});
const report = response.parsed_output;
if (report === null) { ... }     // 解析失败是 null，要判空
```

Zod 同时干两件事：运行时转成 JSON Schema 发给 API，编译时推导出 TS 类型。
`.describe()` 里的文字**会发给模型**，写清楚能显著提升抽取质量。

这套 schema 机制就是后面**工具调用**的基础 —— 定义工具就是定义"模型要填的表单"。
